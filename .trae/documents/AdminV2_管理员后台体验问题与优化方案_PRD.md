# 管理员后台体验问题与优化方案（RBAC规范版 PRD）

## 1. 背景与目标
当前后台以“admin 单角色”实现基础管理（用户/商品/订单/售后），存在权限粗粒度、列表全量加载、缺少审计与批量能力等问题，难以支撑真实后台管理场景与论文要求的“权限审计/操作追踪/可用性提升”。

### 1.1 目标（可用性指标）
以“同等业务能力更少步骤、更短时间、更低错误率”为导向，目标如下（需在可用性测试中验证）：
- 操作步骤减少 ≥ 30%
- 核心任务完成时间缩短 ≥ 50%
- 错误操作率 ≤ 1%
- 管理员满意度 ≥ 4.5/5

### 1.2 非目标
- 不在本轮实现复杂 BI 报表引擎、全量权限策略表达式、工作流编排平台。
- 不在本轮实现多租户/多站点隔离。

## 2. 现状问题系统性分析（体验/缺失/逻辑）
### 2.1 体验问题（UX）
1) 权限反馈不友好：非管理员可进入后台壳，再被接口 403 打断，造成“能进不能用”。  
2) 列表性能与可用性：用户/订单接口后端全量返回，前端本地过滤；数据增大后卡顿、筛选延迟、移动端体验变差。  
3) 关键操作分散：订单明细、售后、状态变更入口分散，缺少“任务导向”的工作台视图（如待发货、待售后）。  
4) 缺少一致的操作确认/撤销策略：删除、改角色、改订单状态属于高风险操作，确认文案与可追溯性不足。  

### 2.2 功能缺失
1) 权限分级体系缺失：仅 user/admin 二值，无法满足“平台管理员/商品管理员/订单管理员/审核员/数据分析员”分工。  
2) 批量操作缺失：批量改状态、批量上下架、批量删除、批量分配角色/重置密码等。  
3) 搜索筛选机制薄弱：缺少后端分页、排序、组合筛选；缺少“保存筛选条件/快速筛选”。  
4) 操作日志追踪缺失：无“谁在何时对什么对象做了什么改变”的审计日志与权限审计报表。  
5) 内容审核模块缺失：缺少对评价/售后等用户生成内容的审核与处理工作台。  

### 2.3 逻辑缺陷与风险
1) JSON 序列化风险：订单/用户数据包含 datetime/ObjectId，直接返回易导致 500。  
2) 状态机缺失：订单状态更新只校验枚举，不校验合法流转（pending→paid→shipped…），易产生不一致数据。  
3) 最后管理员保护缺失：角色变更未限制“降级最后一个管理员”、未限制“管理员修改自己权限”。  
4) 会话混淆风险：前台与后台共用 token key，易互相覆盖导致权限误判与体验问题。  

## 3. 用户角色与 RBAC 权限体系（重新设计）
### 3.1 角色（Roles）
- 超级管理员（SuperAdmin）：角色/权限管理、系统设置、所有资源读写、审计查看。
- 运营管理员（OpsAdmin）：用户管理、内容审核、售后处理、基础统计查看。
- 商品管理员（ProductAdmin）：商品新增/编辑/上下架/库存调整、商品导入导出。
- 订单管理员（OrderAdmin）：订单查询/发货/状态流转、退款/售后处理（按授权）。
- 审核员（Reviewer）：评价/内容审核、违规处理（只读订单/用户敏感字段受限）。
- 数据分析员（Analyst）：只读统计与导出（无写操作）。

### 3.2 权限（Permissions）模型
采用 RBAC（Role-Based Access Control）：
- Permission = Resource + Action
- Resource 示例：user, product, order, after_sale, review, audit_log, role, permission, dashboard
- Action 示例：read, create, update, delete, approve, reject, export, assign_role, ship

示例：
- `order.read`, `order.update_status`, `after_sale.approve`, `user.assign_role`, `audit_log.read`

### 3.3 权限分配规则
- 用户可拥有多个角色（user_roles）。
- 接口层做“权限点校验”（细粒度），替代目前仅校验 role=admin。
- 默认采用“最小权限原则”，新增管理员需分配角色后才可使用对应模块。

## 4. 信息架构与导航逻辑（IA）
### 4.1 导航结构（建议）
侧边栏一级菜单：
1) 概览（Dashboard）
2) 用户与权限
   - 用户管理
   - 角色管理
   - 权限审计
3) 商品管理
   - 商品列表
   - 上下架/库存
4) 订单与售后
   - 订单列表
   - 待处理任务（待发货/待售后/待取消）
5) 内容审核
   - 评价审核
6) 审计日志
7) 系统设置（仅 SuperAdmin）

### 4.2 全局交互
- 顶部：全局搜索（订单号/手机号/商品名），快捷跳转详情页。
- 面包屑：显示当前位置，支持返回。
- 统一筛选栏：筛选项可折叠，支持“保存筛选/一键清空”。

## 5. 关键模块功能优化方案
### 5.1 用户管理
- 服务端分页 + 搜索：手机号/用户名/角色筛选；排序（创建时间）。
- 批量操作：批量赋予角色、批量禁用/启用（如引入状态字段）。
- 详情抽屉：聚合展示用户信息、订单概览、风险标签（可选）。
- 保护策略：禁止降级最后一个 SuperAdmin；禁止修改自己关键权限；关键操作需二次确认并写入审计日志。

### 5.2 商品管理
- 服务端分页 + 组合筛选：分类/价格区间/库存阈值/关键词；排序（创建/销量/价格）。
- 批量操作：批量上下架、批量改分类、批量调库存、批量删除（需权限）。
- 草稿/发布：新增 `status=draft|published|archived`，减少误上架。
- 导入导出：CSV 导入/导出（仅 ProductAdmin+）。

### 5.3 订单管理与售后
- 订单状态机：定义合法流转（pending→paid→shipped→delivered→completed），以及取消/售后互斥规则。
- 任务工作台：按“待发货/待售后/待取消申请”聚合视图，支持一键处理。
- 批量操作：批量发货（填写物流）、批量改状态（受状态机限制）。
- 售后流程：完善售后状态（pending→approved/rejected→completed），支持备注与证据附件（可选）。

### 5.4 数据统计
- 概览卡片：用户/商品/订单/销售额 + “今日/近7天/近30天”切换。
- 趋势图：订单量与销售额趋势（轻量版即可）。
- 导出：分析员可导出汇总数据。

### 5.5 操作日志与权限审计（新增）
- 审计日志：记录 actor、action、resource、target_id、before/after diff、result、ip、ua、request_id、timestamp。
- 权限审计：支持按管理员查看“拥有的角色/权限点”、按权限点查看“有哪些人有此权限”。

## 6. 可用性测试方案（用于指标验证）
### 6.1 任务集合（核心任务）
T1：查询某用户并将其赋予“订单管理员”角色。  
T2：筛选“待发货订单”并完成发货操作。  
T3：筛选“售后待处理”并批准一个售后请求。  
T4：查询某商品并批量下架一组商品。  
T5：查看近 7 天销售额趋势并导出报表。  

### 6.2 指标采集方法
- 步骤数：按“点击/输入/确认”记为 1 步；前后对比统计均值。
- 完成时间：从进入页面到提示成功的时间（前端埋点或录屏计时）。
- 错误率：错误操作/回退/失败请求占比（事件埋点 + 审计日志对照）。
- 满意度：SUS 或 1~5 量表问卷。

### 6.3 验收口径
指标达标以“至少 5 名受试者、每个任务至少 3 次执行”的均值/中位数为准；若不达标，按日志与录屏定位摩擦点迭代。
